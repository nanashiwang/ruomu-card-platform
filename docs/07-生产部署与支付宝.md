# 生产部署与支付宝官方支付

本方案使用 `deploy/docker-compose.prod.yml`：一个 Nginx HTTPS 网关按域名转发到独立的用户站、管理站和 API 容器，Redis 与 API 数据使用持久卷。只有网关发布 80/443，内部 8080、前端 80 和 Redis 6379 不发布到宿主机。

## 1. 上线准备

服务器需要 Docker Engine、Docker Compose v2.20+（支持 `config --format json`、`up --wait`）、Python 3.9+、OpenSSL 1.1.1+ 和 curl。构建镜像需要访问镜像仓库、Go 模块代理及 npm。此方案由该 Nginx 直接终止公网 TLS；如另接 CDN 或负载均衡，需另行配置可信代理及真实 IP。

准备三个不同域名，分别解析到服务器：

| 配置 | 示例 | 用途 |
| --- | --- | --- |
| `USER_DOMAIN` | `shop.example.com` | 用户站、商品、支付返回页 |
| `ADMIN_DOMAIN` | `admin.example.com` | 管理后台 |
| `API_DOMAIN` | `api.example.com` | API、支付宝异步通知 |

示例域名不能直接部署。仅配置实际可达的 DNS 记录；如果发布 AAAA，也必须确保 IPv6 入口可用。开放公网 TCP 80/443，确认没有其他进程占用；不要为回调路径启用登录、验证码或 WAF 浏览器挑战。

为每个域名签发公开受信任、域名匹配的 TLS 证书，并把完整链和私钥部署到服务器仓库之外，例如：

```text
/etc/ruomu/tls/
  shop.example.com/fullchain.pem
  shop.example.com/privkey.pem
  admin.example.com/fullchain.pem
  admin.example.com/privkey.pem
  api.example.com/fullchain.pem
  api.example.com/privkey.pem
```

可使用一张覆盖三个域名的 SAN 证书或各自独立的证书。私钥必须无密码、限制文件权限，且可由容器 root 读取。挂载整个目录为只读；使用软链接时目标也必须在挂载范围内。证书由服务器的证书管理工具签发/续期，本仓库不包含私钥、ACME 账户或自动签发凭据。续期后按下文检查并 reload。

## 2. 环境变量

```bash
cp .env.example .env
chmod 600 .env
# 编辑 .env：域名、TLS_CERT_DIR、回调 URL、各项随机密钥和初始管理员密码
# 每个应用/JWT/Redis 密钥分别生成，不能复用：
openssl rand -hex 32
```

根目录 `.env` 由 **Docker Compose** 读取，不使用 shell `source`。含 `$` 等字符的密码应按 Compose env-file 规则加单引号，避免插值；随机十六进制密钥没有此问题。已导出的同名 shell 环境变量会覆盖文件，检查脚本校验的是 Compose 最终解析值，且不会输出完整配置或密钥。

| 变量 | 实际作用与要求 |
| --- | --- |
| `USER_DOMAIN` / `ADMIN_DOMAIN` / `API_DOMAIN` | 网关虚拟主机与证书目录名；小写域名，不带协议、端口、路径，三者不同 |
| `TLS_CERT_DIR` | 服务器证书目录的绝对路径，只读挂载到网关 |
| `HTTP_BIND` / `HTTPS_BIND` | 默认 `0.0.0.0`，网关宿主机绑定地址 |
| `HTTP_PORT` / `HTTPS_PORT` | 默认 `80` / `443`；生产公网仍须提供标准 443，变更端口仅用于本机测试或已有端口映射 |
| `APP_SECRET_KEY` | 敏感数据加密密钥，至少 32 字符；备份后妥善保存，已有数据部署勿随意更换 |
| `JWT_SECRET` / `USER_JWT_SECRET` | 管理员与用户 JWT 密钥，各自独立且至少 32 字符 |
| `REDIS_PASSWORD` | 至少 32 字符，同步应用于 Redis 服务、API、worker 和健康检查 |
| `DEFAULT_ADMIN_USERNAME` / `DEFAULT_ADMIN_PASSWORD` | 仅初始化空库生效；用户名必填，密码至少 16 字符、含大小写字母及数字；已有管理员不因 env 更改而重置 |
| `ALIPAY_NOTIFY_URL` / `ALIPAY_RETURN_URL` | **部署校验的期望值**，不是应用运行时自动注入的支付参数；需手动填入管理后台支付渠道 |
| `DATABASE_DRIVER` / `DATABASE_DSN` | 默认 `sqlite` + `/app/db/ruomu.db` 持久卷；可改为 `postgres` + 外部连接 DSN，需自行提供可达数据库 |
| `REDIS_PREFIX` | 默认 `ruomu`；此 Compose 使用独立 Redis，API 与队列共享该服务 |
| `JWT_EXPIRE_HOURS` | 管理员 JWT 有效小时数，默认 `24` |
| `APP_VERSION` / `APP_TOTP_ISSUER` | API 构建版本标记 / 2FA 显示名称 |
| `EMAIL_ENABLED` / `CAPTCHA_PROVIDER` | 默认 `false` / `none`；启用其他服务前还需补齐对应运行时配置 |

生产固定 `SERVER_MODE=release`。前端使用同域 `/api/v1`，由网关直接转发给 API，无需跨域 API 地址。根目录 `VITE_*` 不会被前端 Docker 构建消费，构建上下文也排除了本地 `.env*`，避免把本地开发地址或敏感值打进镜像。

旧草案的 `API_PORT`、`USER_PORT`、`ADMIN_PORT` 已由网关入口替代；`API_BASE_URL`、`PUBLIC_SITE_URL`、`ADMIN_SITE_URL`、`PAYMENT_CALLBACK_URL`、`DATABASE_URL`、`REDIS_URL`、`UPLOAD_PATH` 没有被生产 Compose 消费，已从示例移除。旧部署升级时先补齐新变量和证书，保留相同 Compose 项目名及数据卷；不要执行 `down -v`。若曾配置非空 Redis 密码，旧草案仅传给客户端，新配置会同时启用服务端认证。

## 3. 支付宝渠道与路径契约

以表中的示例域名为例，在 `.env` 与管理后台「支付渠道 → 官方 → 支付宝」填写相同的值：

| 字段 | 完整地址 | 接收方与含义 |
| --- | --- | --- |
| `notify_url` / `ALIPAY_NOTIFY_URL` | `https://api.example.com/api/v1/payments/callback` | API `PaymentCallback → HandleAlipayCallback`，接收支付宝表单 POST，验签、校验应用归属并处理支付结果 |
| `return_url` / `ALIPAY_RETURN_URL` | `https://shop.example.com/pay` | 用户 SPA 的 `/pay` 页面；服务端下单时附加 `alipay_return`、订单/充值关联参数，网关完整保留查询字符串 |

部署检查要求上述域名及路径严格匹配，不能添加尾斜杠、`?channel_id=...`、fragment 或其他查询参数。管理后台「回调路由」里的自定义支付回调应留空，以使用默认路径。**如果已有自定义支付回调，应用会屏蔽默认路径并返回 404；上线后的探针会因此失败。** 如确实需要自定义路径，需同时调整本文契约、校验器、渠道与路由测试，不能只改 `.env`。

`notify_url` 不能填成 `/pay`、`/api/payments/callback` 或支付宝网关地址。`return_url` 不能填 API 域名，也不能写成 `/#/pay`。HTTP 入口返回保留方法的 308，但支付宝渠道必须直接使用 HTTPS，不依赖通知端跟随跳转。

渠道的 `app_id`、应用私钥、支付宝公钥、签名方式及网关在管理后台配置；`.env` 不会自动创建渠道、覆盖数据库，也不会替你配置支付宝开放平台。使用该商户实际开通的支付产品对应交互模式，生产网关为 `https://openapi.alipay.com/gateway.do`；跳转模式需要 `return_url`，本部署规范统一要求两个 URL 均填写。不要把真实密钥写入示例、脚本、镜像、Git 或提交记录。

浏览器到达 `/pay` 不表示付款成功。已验签且业务处理成功的通知返回纯文本 `success`；未找到交易或验签失败返回纯文本 `fail`。验收时以 API 支付状态与通知处理结果为准。

## 4. 一键检查与部署

```bash
# 仅检查，不构建/启动业务容器；会临时运行网关执行 nginx -t
./scripts/deploy.sh --check

# 检查通过后构建、启动，并等待健康检查；随后验证公网 HTTPS 路由
./scripts/deploy.sh

# 已上线后可单独复查（使用公网 DNS，严格验证 TLS，不使用 -k）
python3 scripts/check-deployment.py --online
```

支持 `ENV_FILE=/绝对路径/生产.env` 和 `COMPOSE_FILE=/绝对路径/compose.yml`。自定义文件必须保留此生产服务结构；首次运行可能拉取网关镜像。

前置检查包括：必填变量和非示例密钥、域名格式及隔离、两个 URL 的精确契约、内部服务无公开端口、Redis 密码一致、证书日期/域名/公私钥匹配、至少 7 天剩余有效期及 `nginx -t`。本地证书检查不等于公开信任链或公网可达；这些由部署后的 `--online` 检查完成。公网检查失败会使部署命令非零退出；已启动的容器及数据保留，修复原因后重新检查，不自动删库或回滚。

在线探针依次通过三个 HTTPS 域名 POST 到默认回调路径，使用随机且不存在的订单号与无效签名，要求 **HTTP 200 + `text/plain` + 精确 `fail`**。这证明表单到达支付宝处理器，而不是 SPA 的 HTTP 200、登录页、重定向或错误路径。它同时检查 API `/health`、用户 `/pay?alipay_return=1...` 与管理站登录页。探针会产生少量「交易不存在」日志，不会改变真实订单，也不会发起支付宝交易。

常见失败：

- `404`：路径错误，或后台启用了自定义回调路由。
- `200` HTML：请求落到前端 SPA，检查 `/api/` 代理。
- `301/302/308`：渠道未直接使用最终 HTTPS URL，或外层网关做了额外重定向。
- `401/403`：外部认证、WAF 或访问控制拦截。
- `502`：API 容器/Docker DNS/上游连接异常。
- TLS 失败：证书域名/有效期/完整链、DNS、443、防火墙或错误 AAAA 记录。

证书续期后执行：

```bash
./scripts/deploy.sh --check
docker compose --env-file .env -f deploy/docker-compose.prod.yml exec gateway nginx -s reload
python3 scripts/check-deployment.py --online
```

使用非默认 env/compose 时，续期命令也需使用相同文件。不要把证书文件复制进仓库；仓库已忽略 `.env*`（保留 `.env.example`）、`deploy/tls/`、`*.pem`、`*.key`。

## 5. 可重复的本地验证与上线验收

```bash
python3 -m unittest discover -s scripts/tests -p 'test_*.py'
(cd apps/api && go test ./internal/router ./internal/http/handlers/public ./internal/payment/alipay ./internal/payment/provider ./internal/service)
python3 scripts/tests/docker-routing.py
```

Docker 测试会构建真正的生产三端镜像、生成临时 SAN 证书和随机测试凭据、使用随机本机端口及独立 Compose 项目/数据卷，验证 TLS/SNI、三个域名通知、API 处理器日志、HTTP 308、SPA 路由和 Redis 认证，最后仅删除该测试项目的容器及数据卷。不会读取生产 `.env`，不会把自签证书加入系统信任，也不会联系支付网关。

这些测试证明部署与路由可用；商户签约、正式渠道配置、公开证书/DNS、真实支付与发货仍需在实际生产环境验收。上线后用受控的小额订单确认通知返回 `success`、订单状态正确且重复通知不重复发货，并确认返回页查询到实际支付结果。本次配置不改变支付业务逻辑、数据库结构或 API 接口。

# 订单发票：申请、审核与邮件交付

## 使用流程

登录用户进入“我的订单 → 订单详情 → 订单发票”。classic 和 vault 模板均提供同一个申请组件。填写个人/企业抬头、企业税号、接收邮箱和备注；金额、币种来自订单，不接受前端指定金额。

仅允许已付款、金额大于零、未退款的主订单。拒绝子订单重复开票、游客订单、取消/退款订单；已退款子订单也阻止主订单申请。每个订单只有一条申请，驳回后用户修改原申请重新提交。游客订单暂不开放申请。

后台“订单管理 → 发票管理”按订单号、申请状态查询。超级管理员可操作；预置财务角色有审核、上传、发送权限。继承只读审计权限的后台角色可查看，系统管理员与运营角色不会额外获得财务写权限；自定义角色可由权限管理单独授权。

1. 核对订单及抬头，选择通过或填写原因驳回。
2. 在外部完成开票后上传 PDF（最大 5 MiB）。服务端校验大小与 PDF 文件签名/结束标记；不代替人工核对发票真实性和内容。文件保存后成为“已开票”，邮件仍是“待发送”。
3. 下载核对附件，再点击“确认发送至上述邮箱”。发送使用后台已有 SMTP 设置，正文和附件通过同一邮件发送。系统不自动生成发票，也不连接税务开票服务。
4. 邮件状态单独显示待发送、发送中、发送失败或邮件已提交发送。失败可重试；SMTP 成功代表邮件服务器已接受，不代表收件人已读或必定进入收件箱。

申请、审核、上传及发送会核对订单资格；后三步还核对申请时金额和币种快照。已开票后退款需要人工处理原票据，系统不自动红冲或换票。上传的 PDF 不允许覆盖；上传前需核对文件。

## 接口与文件边界

- 用户：`GET/POST /api/v1/orders/:order_no/invoice`，`GET /api/v1/orders/:order_no/invoice/download`。
- 管理：`GET /api/v1/admin/invoices`，`POST /api/v1/admin/invoices/:id/review`（decision 为 approve/reject）、`POST .../:id/file`（multipart 第一个字段为 file）、`POST .../:id/send`、`GET .../:id/download`。
- 用户入口复用现有用户和租户订单查询；不能访问其他用户或其他分销站的申请、文件。
- PDF 存在 `order_invoices.file_data` 私有列。JSON 不返回文件内容，列表/用户详情查询不读取该列；下载返回 attachment、no-store、nosniff，公共上传目录没有副本。数据库备份包含发票资料，需延续数据库访问与备份保护。
- 状态更新使用数据库条件更新。邮件发送使用持久化十分钟占用，SMTP 连接最多五秒、连接后全流程二十秒。进程中断后，十分钟后刷新可重试。SMTP 接受后数据库写回失败仍存在结果不确定窗口；重试前需核对邮箱，不能保证严格只发送一次。

## 既有环境的增量迁移

正常 API 启动沿用项目 AutoMigrate，新安装会创建发票表。固定版本容器更新工具会检查数据库副本无变化，因此既有生产环境不能直接跳过迁移检查升级。

本版本增加短路命令：

```bash
/app/ruomu-api migrate-invoices --apply
```

该命令读取当前目录的 `config.yml` 和既有数据库环境变量，事务内只创建/对齐发票表并补充财务角色三条发票写权限。它不启动 HTTP、worker、邮件或默认管理员初始化；参数不正确时不连接数据库。可以重复执行，成功标志为 `INVOICE_MIGRATION_SUCCESS`。

上线顺序：

1. 下载并验证本次 Release 的固定镜像和校验清单，按现有方式检查配置、数据库位置、共享依赖和运行中的任务。
2. 在数据库一致性备份副本上，用新版本 API 的上述命令迁移，检查旧订单和其他业务数据未变。SQLite 复制必须使用在线备份或停写后的完整备份，不能漏掉 WAL。
3. 安排停写窗口，停止 API 及所有独立 worker，保留现有数据库一致性备份。用新 API 镜像的一次性容器挂载经过核实的原配置、数据库卷并执行上述命令；挂载路径和数据库环境变量必须与原 API 一致。迁移成功后按原方式启动旧 API，保持业务兼容。
4. 执行现有 `rcard-update <完整SHA>`，由原工具重新核对副本启动无变化、三端健康和回滚条件。不得修改其数据库签名门禁，也不得用迁移后的副本覆盖生产数据库。
5. 确认后台财务权限、用户申请和测试订单的邮件交付。使用自己的测试邮箱，勿对客户补发测试邮件。

回滚保留新增表和发票资料，恢复旧应用镜像，不删除新表、不覆盖新订单。若旧镜像的副本兼容检查失败，按现有工具中止并人工排查。本次开发与 GitHub Release 不代表已经执行生产迁移或部署。SQLite 迁移有自动化测试；PostgreSQL 使用 GORM 对应方言，生产使用前仍需在该环境副本演练。

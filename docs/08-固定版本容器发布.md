# 固定版本容器发布

代码提交到 GitHub 后，`卡台测试与镜像发布` 工作流运行 Go 测试、部署工具测试和决策笔记校验，然后构建 API、用户前台、管理后台三个 linux/amd64 镜像。两个前端在 Docker 构建阶段执行类型检查与生产构建。真实三端路由、模拟支付回调、SQLite 副本兼容检查、手动回滚和注入失败恢复全部通过后，main push 才发布 `card-<完整提交 SHA>`；PR 不发布生产产物，push 不自动连接生产服务器。

## 产物

- 三个 GHCR 镜像分别为 `ghcr.io/nanashiwang/ruomu-api`、`ruomu-user`、`ruomu-admin`，标记同一提交 SHA。
- `release.json` 包含每个镜像的仓库 digest、发布端 ID、归档 SHA256 与应用源码指纹。
- `api.tar.gz`、`user.tar.gz`、`admin.tar.gz` 是已经测试的镜像导出包，用于 GHCR 匿名拉取不可用时回退，不需要上传 GitHub token 到服务器。
- `container_release.py` 是仅依赖 Python 标准库的部署工具；服务器需 Python 3.10+、Docker Compose v2、git、curl、x86_64、至少 2 GiB 磁盘及 704 MiB 可用内存。
- 已公开发布的版本不可重建覆盖。发布过程失败时可能保留 draft，只能补齐尚未公开的 draft；回滚使用已有镜像。

## 首次接入现有服务器

新工具与 `scripts/deploy.sh` 分开，后者仍是原有完整网关模板的安装/检查入口。不要在共享服务器直接用仓库新网关模板覆盖当前部署。

新工具只接管已有 `ruomu-card-platform` 项目的 `api`、`user`、`admin`。从运行中容器标签定位现有 Compose 文件和原项目工作目录（例如安装目录下的 deploy），在该目录上下文解析相对挂载路径；原工作目录缺失、三端不一致、符号链接或越界时拒绝。校验配置哈希一致，读取现有解析后的配置并保存在 0700 目录下的 0600 文件中；只替换三端镜像，保留端口、网络、数据卷、挂载、密钥及其他服务。Compose 配置快照含生产秘密，只能留在服务器受保护目录，不能发送到聊天或提交 Git。

未知/多 Compose 覆盖布局、配置与容器漂移、缺失源代码、应用源码与发布指纹不一致、非 SQLite、自定义 DSN、API bind mount、其他运行容器共享数据库等情况会停止，需先核对。源码指纹不等于旧二进制的来源证明；首次切换还必须核对实际运行版本和业务入口。若现有源码缺失或有业务差异，不能简单从 GitHub 覆盖文件来绕过门禁。

审核对应 Release 后，在服务器下载固定版本脚本并核对维护者给出的 SHA256：

```bash
python3 /tmp/ruomu-container-<SHA>.py preflight
python3 /tmp/ruomu-container-<SHA>.py deploy <40位提交SHA>
```

操作期间 API 短暂停止，API 同进程 worker 一并收到正常停止信号，前台和后台页面仍可打开但业务请求暂不可用；外部通知依赖供应商重试，不宣称零停机或真实支付已验收。

停止后保留 SQLite 一致性备份，在服务器本机副本中用新镜像启动 API，禁用网络、Redis、任务队列、邮件与默认管理员创建。新镜像不得改变副本的逻辑结构或任何业务行，变化即拒绝切换；副本试运行不向外部支付系统发送请求。生产数据库不会上传 GitHub，也不会作为镜像层打包。

之后使用现有配置以 `--no-build --no-deps --pull never` 切换三端，检查各自健康、镜像引用、受保护配置与其他项目容器身份/启动时间。Redis 和网关不重建，不执行 Compose down 或任何全局 prune。成功会输出 `DEPLOY_SUCCESS`、`ROLLBACK_DIRECTORY` 和临时测试容器归零。

## 回滚与限制

```bash
python3 /tmp/ruomu-container-<SHA>.py rollback /opt/ruomu-backups/container-releases/<本次备份目录>
```

回滚恢复程序镜像及配置，**不恢复旧数据库覆盖新订单**。旧 API 必须先在当前数据库副本上通过无变化启动检查；不通过就拒绝回退，需单独的迁移恢复方案。失败自动恢复同样遵守此限制，恢复失败会明确退出，不能声称业务已恢复。SIGKILL/主机断电无法保证自动恢复，需要按备份记录人工处理。

首次接管刻意只支持“保持应用源码一致的构建方式迁移”；后续使用服务器上的 current.json 核对当前三端镜像，不再依赖保留的旧源码版本，可以发布经 CI 验证的业务改动，但新旧镜像仍必须通过数据库副本无变化启动检查。数据库结构变更需要单独迁移方案，不能靠修改源码副本或版本记录欺骗校验。健康检查和路由测试不代表真实交易和发货完整验收。

## 清理边界

部署不删除任何缓存、卷、旧镜像或备份。上线验收后，可按用户先前要求另行审核 `ruomu-go-build-cache`、`ruomu-go-build-cache-cgo`、`ruomu-go-mod-cache` 和测试构建镜像。无容器引用只是一项证据，不能代替用途与重建能力检查。构建迁移不会自动释放磁盘。

## 容器日志限额与只读磁盘审核

新版本部署仅为 `api`、`user`、`admin` 的 `json-file` / `local` 日志驱动设置每份最多20MiB、最多3份，已有更小的限额和其他选项保持。显式使用其他驱动（含 `none`）时不替换，输出保留提示；Redis、网关和其他项目不改。配置写入新版本快照，切换后检查实际 Docker 参数，失败按原流程回滚。回滚恢复旧程序及旧日志策略，可能恢复为无上限。日志轮转会淘汰最早的容器输出；不宣称保留了所有历史日志。

程序自身 `app.log` 已有轮转，这一轮不变。限额随正常发布重建三个容器才生效，不修改 Docker daemon、不手工截断日志。日志策略与数据卷内容互相独立。

Release 同时提供标准库脚本 `storage_audit.py`，在服务器以 root 执行，只输出整机磁盘余量、三端实际日志参数，以及四个固定候选的存在状态、ID/大小、所有容器（含停止容器）引用、发布/回滚记录引用及缓存布局。不会打印环境值、日志正文或数据库内容，也不会启动容器或删除对象。

```bash
python3 /tmp/ruomu-storage-audit-<SHA>.py
```

零引用、符合缓存目录形状、历史创建时间均不足以证明可以删除；最后使用时间没有可靠来源时标为未知。构建脚本依赖、离线依赖能否重建仍需核实。工具只给审阅依据，不提供全局 prune 或删除参数。访问服务器不可用时不能用旧记录当实时审核结论。

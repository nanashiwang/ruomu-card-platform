# Agent Note: 卡台固定版本容器发布与共享服务器迁移

Status: proposed

## Problem

共享生产服务器承担 Go 与前端构建，遗留镜像和缓存占用磁盘；现有 GitHub 工作流不执行应用测试或发布镜像。需要在 GitHub 完成验证和打包，生产只下载确定版本并保留恢复路径。

## Existing capabilities and impact

复用 scripts/build.sh、三端 Dockerfile、scripts/check-deployment.py 与 scripts/tests/docker-routing.py。现有生产 Compose 增加了网关，但已观察服务器仍使用旧入口，不能套用仓库模板替换线上网络。API 在启动时调用 AutoMigrate，发布成功不能仅以进程存活判断。

检索活跃笔记，仅有能力审查/笔记工作流规则，与本次发布机制不重叠；保留原笔记。影响三端打包和部署工具，不改变订单、支付、库存、权限及数据库业务模型。数据来源是服务器已有 Compose 配置、实际容器与 SQLite 数据卷；生产凭据和数据库不会进入 CI。

## Proposal

应用测试通过后构建三个镜像，真实路由演练通过才发布不可变 release manifest、GHCR digest 及校验归档。服务器从实际现有 Compose 项目提取配置并核对容器配置哈希，仅替换 api/user/admin 镜像，redis、gateway 及同机其他项目保持原状。

首次部署严格要求服务器 API 源码与发布版相同；停止 API 后在离线数据库副本上执行新镜像启动，要求逻辑数据库完全不变，之后才切换。备份和回滚保留数据，绝不自动恢复旧数据库覆盖新订单。回滚也先检查当前数据库与旧镜像兼容。未知布局、源码差异、配置漂移、迁移变化均阻止执行。

## Alternatives considered

- 保留服务器 --build：现有路径简单，但继续占用共享主机资源与缓存空间。
- 直接应用仓库生产 Compose：可复用完整网关配置，但与线上入口不同，可能抢占其他项目端口。
- 出错自动恢复数据库：恢复程序和数据状态最直接，但可能覆盖已产生的新订单，不能作为通用回滚策略。

## Acceptance criteria

后端测试、两端类型检查与构建、部署配置测试、真实三端路由/模拟回调、隔离迁移/回滚演练成功；所有测试容器与子进程退出。版本标签、平台、镜像digest和归档哈希校验，错误信息不输出秘密。代码提交和发布标题中文。首次上线需真实服务器预检通过；缓存删除另行审阅，不随部署执行。

## Risks

真实服务器入口与GitHub模板不一致，需要部署前核验。严格源码一致门禁不支持顺带发布业务改动。短暂维护可能让支付通知重试；不宣称零停机或真实支付已验收。缓存不会因迁移自动消失，删除需另行批准。

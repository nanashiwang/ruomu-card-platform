# Agent Note: 发票申请运营通知

Status: implemented

## Problem

库存已有通知中心、定时检查和阈值配置，发票申请缺少运营提醒。

## Decision

扩展现有通知场景 invoice_requested，默认关闭，由管理员明确开启；复用 SMTP、收件人、模板、日志和队列。申请事务成功后入队，驳回重新申请也提醒，重复或失败申请不提醒。邮件只带订单号和金额，不带税号或发票附件。通知失败不回滚已提交申请。

活跃笔记检索：[订单发票笔记](2026-11-10-order-invoices.md)与本次部分重叠，保留其审核与交付决定；其他库存相关命中是发布隔离边界，与本次无关。影响申请服务、通知配置、后台通知页面与组装入口，保持权限和三端边界。

## Alternatives considered

同步 SMTP 可不依赖 worker，但延迟和失败会阻塞申请；新建通知模块会重复收件人和日志管理。因此沿用队列。事务 outbox 可防入队丢失，但需要迁移和投递调度，本次沿用已有尽力入队约定并记录失败。

## Consequences

验证首次申请、重复、失败、驳回重提与队列失败；配置补丁持久化、模板、开关和重试测试通过。`./scripts/build.sh` 完成全量后端测试、API 编译与三端构建；随后新增开关/重试测试单独运行通过。默认关闭新场景，旧配置兼容，不改数据库 schema。

发票通知使用 Force 跳过通用时间去重（不绕过场景或渠道开关），防止重提被吞和首次发送失败后的队列重试被时间去重拦截。代价是多收件人部分成功后重试可能重复提醒，沿用队列最多五次重试；申请事务本身拒绝重复提交。需要 Redis/worker 和 SMTP；事务成功后进程崩溃或入队失败可能漏报，记录错误日志且保留后台待办。邮件服务器接收不等于到达收件箱；未向真实邮箱试发或操作生产部署。

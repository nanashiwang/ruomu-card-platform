# Agent Note: 卡台容器日志限额与限定范围磁盘审核

Status: implemented

## Problem

卡台迁到固定镜像后，旧构建缓存仍需审核，容器标准输出日志也可能继续累积。用户要求先完成清理审核和日志上限，再回到检测站，不扩展成全机清理。

## Existing capabilities and impact

[程序日志](../../../../apps/api/internal/logger/logger.go)已用 lumberjack 轮转；[发布工具](../../../../scripts/container_release.py)保留原配置、数据及回滚，适合在新配置中加入单容器限额。现有发布笔记继续适用，本笔记仅补充日志策略和只读审核边界。三个已识别 Go 缓存卷及一个测试镜像仍只是候选，用户尚未批准最终删除。

## Decision

只为 api/user/admin 的 json-file 或 local 驱动限制每份20MiB、最多3份，沿用现有更小限制及其他日志选项；其他驱动和禁用日志保持原样并说明未调整。旧回滚配置原样保留，实际运行参数不符则按原流程恢复。

新增只读存储审核入口，固定4个候选名称，检查所有容器（含停止的）引用、私有发布/回滚记录、缓存目录结构、实际日志配置和磁盘余量。输出只含大小、标识、检查结果，不输出环境值、数据库内容或日志正文；不提供删除功能。

## Alternatives considered

- 全局 Docker 日志配置：一次覆盖所有容器，但会改变同机格物、酒馆等项目且需要全局运维，拒绝。
- 直接截断现有日志或清空缓存卷：能立即腾空间，但绕过用途核查且影响日志证据，拒绝。
- 把程序文件日志也一并改小：有已有轮转，本轮没有依据重新调整其保留策略，保持原样。

## Consequences

只有卡台三个应用的本地文件日志获得上限，不涉及共享daemon、Redis、网关或其他项目。已有更小限额和其他日志选项保留。轮转会淘汰最早的容器输出，正常发布重建应用容器后生效；旧版本回滚也恢复旧日志策略。程序文件日志既有轮转保持不变。

审核工具只提供固定候选的元数据和引用检查，最后使用时间未知则如实标记，缓存布局不等于内容安全或删除许可。服务器访问不可用时不能声称实时审核或清理已完成；生产执行和最终删除仍有独立验收边界。

## Verification

40项本地部署/审核测试、笔记检查通过。CI真实容器证明20MiB/3份策略生效、原策略可回滚，三端路由与数据库副本检查继续通过。CI测试容器和后台进程归零；生产需部署此版本后再次读取实际日志策略，未将CI结果当作生产完成。

# Agent Note: 卡台固定版本容器发布与共享服务器迁移

Status: implemented

## Problem

共享生产服务器承担 Go 与前端构建，遗留镜像和缓存占用磁盘；现有 GitHub 工作流不执行应用测试或发布镜像。需要在 GitHub 完成验证和打包，生产只下载确定版本并保留恢复路径。

## Existing capabilities and impact

复用 scripts/build.sh、三端 Dockerfile、scripts/check-deployment.py 与 scripts/tests/docker-routing.py。现有生产 Compose 增加了网关，但已观察服务器仍使用旧入口，不能套用仓库模板替换线上网络。API 在启动时调用 AutoMigrate，发布成功不能仅以进程存活判断。

检索活跃笔记，仅有能力审查/笔记工作流规则，与本次发布机制不重叠；保留原笔记。影响三端打包和部署工具，不改变订单、支付、库存、权限及数据库业务模型。数据来源是服务器已有 Compose 配置、实际容器与 SQLite 数据卷；生产凭据和数据库不会进入 CI。

## Decision

应用测试通过后构建三个镜像，真实路由演练通过才发布不可变 release manifest、GHCR digest 及校验归档。服务器从实际现有 Compose 项目提取配置并核对容器配置哈希，使用容器记录的原 Compose working_dir 解析相对挂载路径，不假设它就是仓库根目录；目录缺失、不一致或越出允许范围时拒绝。仍要求原配置哈希和环境值完全匹配，仅替换 api/user/admin 镜像，redis、gateway 及同机其他项目保持原状。

首次部署严格要求服务器三端源码与发布版相同；后续以已部署镜像和版本记录一致为门禁；停止 API 后在离线数据库副本上执行新镜像启动，要求逻辑数据库完全不变，之后才切换。备份和回滚保留数据，绝不自动恢复旧数据库覆盖新订单。回滚也先检查当前数据库与旧镜像兼容。未知布局、源码差异、配置漂移、迁移变化均阻止执行。

## Alternatives considered

- 保留服务器 --build：现有路径简单，但继续占用共享主机资源与缓存空间。
- 直接应用仓库生产 Compose：可复用完整网关配置，但与线上入口不同，可能抢占其他项目端口。
- 出错自动恢复数据库：恢复程序和数据状态最直接，但可能覆盖已产生的新订单，不能作为通用回滚策略。

## Consequences

生产服务器不再承担三端构建，更新使用已验证的不可变镜像。首次接管严格检查三端源码和现有配置，后续检查已管理镜像记录。新工具不覆盖现有网关模板，不改变业务 API 或数据库模型，不删除构建缓存。部署有短暂API维护窗口，外部支付通知需要按原供应商机制重试。

SQLite副本必须通过新/旧镜像启动无逻辑变化检查，限制了自动发布的范围；数据库结构变更需要另行处理。程序回滚不覆盖新订单。版本记录和配置快照含秘密，保存在服务器私有目录；生产数据不进入GitHub。源码指纹不能证明旧二进制来源，首次上线仍需核对真实版本和业务入口。

## Verification

本地标准库部署测试和笔记校验通过；GitHub演练验证真实三端镜像、TLS/回调路径、原 deploy 子目录下的相对 nginx 挂载与配置哈希、环境值美元符号、数据库副本不变、手动回滚和注入故障恢复，测试容器与后台进程归零。后续最终提交和main发布必须各自通过同样CI，不能用旧提交结果代替。生产服务器尚未切换，真实环境预检失败必须停止，不声明CI通过等于线上成功。
